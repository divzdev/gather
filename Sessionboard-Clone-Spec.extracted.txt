How to read this document
Every requirement traces back to something observable: a line in the transcript, or a screen in the capture set. Timestamps in the form 4:57 refer to the walkthrough video. Screenshots are the real product, captured from the video, and each caption names the specific elements worth reproducing.
Where the captures contradict what the vendor’s public documentation says, the captures win — they show the version the customer is actually paying for. Section 12 lists those corrections explicitly.
Scope in one line:  Run a call for papers, collect submissions through a public form, have a committee score them, accept the winners, drag them onto a schedule, publish it. Nothing else.

3. Non-functional requirements
These are not boilerplate. They are the reason the customer is shopping in the first place — he complains about the incumbent’s speed four separate times and catches it failing validation twice, on camera.
“part of this I also don’t love is that it’s kind of slow”  — 3:43
“this slowness is part of why I think you guys can probably do a better job than Sessionboard”  — 4:11
“oh my god, this is so slow”  — 7:12

Requirement
Target
Speed
Every admin list or table view interactive in under 500 ms. No full page reloads between program screens. Optimistic UI on status changes and drag-drop. Server-side pagination and indexed filters on every list.
Validation
Client and server validation on every field: required, min/max, length, email, URL, number range, file type and size. Inline errors, focus moves to the first failure, never lose input.
Sane limits
Participant minimums default to 1. The UI must reject min greater than max — see 4.4 for the exact bug the customer hit live.
Autosave
Evaluator scoring saves on selection. Public form drafts persist across sessions.
Public pages
The public form and public agenda are server-rendered and fast. They are what strangers judge.

7.2 Required behaviour
Deadline banner — “Form submissions will be accepted until September 15 at 11:59 PM PDT.” Render in the event timezone with the zone abbreviation shown.
Limit banner — “Submission Limit: 3 submissions per user.”
Account before content — the account step comes second, so every submission is owned by a portal identity from the start. An existing email prompts sign-in and attaches the submission to that account.

Limit enforcement — a submitter at their cap gets a clear message, not a failed submit.
Redirect — on success, offer the portal; auto-redirect after ten seconds if configured.
This is the validation screen.  A stranger judges the whole product here. Validate on blur, validate on submit, keep entered data on error, and move focus to the first failing field.

9.3 Creating a plan
Group
Settings
Configuration
Name, instructions, open or closed, due date per round, anonymised review (hides participant names), reminders, whether evaluators can open uploaded files
Evaluators
Assign evaluators, optionally by tag. Evaluators must already exist on the event; assignments change only while the plan is closed
Session filters
Filter by any standard or custom session field to decide which submissions the plan covers — this is how “this team reviews these submissions” works
Display fields
Which session and participant fields evaluators see, plus custom evaluation questions
Grading
Rating scale, optional weighted rubric whose criteria must total 100%, and a cap on evaluations per submission. Locked once the plan is created — warn on the create screen
9.4 Evaluator experience
Invitation email, magic link, land on the list of assigned plans.
Open a plan to get a queue of assigned submissions.
Read the instructions and the chosen display fields; participant names hidden if the plan is anonymised.
Score against the scale or rubric — selections auto-save.
Add comments, or abstain on a conflict of interest.
Save &amp; Next; a progress meter climbs to 100%.
Hard rules: evaluators see only their assignments, never each other’s scores, never the admin console, and cannot contact participants. Scores are never shown to submitters.
9.5 Summary dashboard
Top-line counts (evaluations submitted, sessions evaluated, active plans, unique evaluators), highest and lowest scoring session, a completion chart, average score by plan, a top-ten list, and a widest-spread list showing submissions where evaluators disagreed most. The last one is the genuinely useful one for a programme committee.

13. Build plan
13.1 Suggested stack
Nothing in this document depends on the choice. A reasonable default: Next.js App Router with TypeScript, Postgres with Prisma or Drizzle, Tailwind with shadcn/ui, dnd-kit for both the builder and the agenda, TanStack Table for list views, Zod schemas shared between client and server so validation cannot drift, a transactional email provider, and S3-compatible storage for headshots and files.
13.2 Order of work
The dependency chain matters. Build downward, and if time runs out, cut from the bottom — a working 1 to 6 is a usable product, whereas a half-built 1 to 10 is not.

13.4 End-to-end acceptance test
One scenario that proves the build. Every step should feel instant.
An admin creates an event, sets dates, timezone and logo.
The admin builds a form: Abstracts with participants, welcome copy, five questions with one conditional, Speaker min 1 max 3, a close date two weeks out, drafts enabled.
The admin copies the public link.
In an incognito window a stranger opens the link, creates an account, fills in the submission and two participants, saves a draft, returns, completes it and submits. A confirmation email arrives.
The submission appears in the admin list as Pending, Source shows the form name, and custom answers are available as columns.
The admin creates an evaluation plan filtered to one track, assigns two evaluators, sets a rubric, opens it and notifies them.
Each evaluator sees only their queue, scores, comments and saves; progress reaches 100%.
The admin reviews the summary, sets the submission to Accepted, and sends an acceptance email. The Notified column updates.
The submitter logs into the portal, sees Accepted, completes a headshot task and updates their biography.
The admin drags the session onto the agenda. A deliberate double-booking raises a conflict, which the admin resolves from the Conflicts tab.
The public agenda shows the session, linked to both participant profiles.
The admin creates an embed, copies the code, and the same agenda renders on an external page — including a deep link straight to one speaker.
